# 架构与平台边界：共享 C 核心、Rust + Slint 与 Web/PWA

本文把 2026-10-01 的“比较 Slint 与 Flutter”对话，以及截至 2026-10-03 本轮纯文本 Review 所确认的架构事实，整理为可持续跟踪的 checkpoints。目标是让后续开发者知道已经有哪些接口、最新建议方向是什么、哪些仍只是建议，以及每一步如何验收。

用户已经明确产品偏好：愿意学习和维护 Rust，不希望长期维护 QML/Qt 或 Dart；原生桌面是主入口，Web 和移动是兼容入口；希望尽量共享 UI 和应用逻辑，并将 Web 提供为普通单页和可安装应用。早期“优先复用 Flutter”或“桌面 Slint 加独立 HTML UI”的建议，属于需求尚未完整明确时的阶段性判断。最新建议方向是 **Rust + Slint 原生桌面，加同源 Slint Web/PWA 兼容入口**；这是尚未正式批准、未实现完整落地的技术方案。独立简化 HTML 界面是实际兼容测试失败后的回退建议。产品偏好已确定，不等于用户已经批准这套架构或实施计划。

本文只记录架构和平台契约。具体源码问题、已落盘修复和回归测试源文件的详细台账见 [代码 Review 与修复](03-code-review-and-fixes.md)。框架比较、历史测量口径和选择过程见 [框架选择](01-framework-decision.md)；发行顺序见 [发行、更新与路线图](04-release-update-and-roadmap.md)；跨文档登记见 [checkpoints 与验证](05-checkpoints-and-validation.md)。所有“已存在”均指静态源码中存在，“源码修复”不等于已经通过运行验证。

本轮没有执行编译、构建、自动化测试或浏览器运行验证。已有二进制、WASM 文件和历史 smoke 结果不能用来证明修改后的源码已经正确。外部框架与浏览器支持结论，只按 **2026-10-01 历史讨论**保存；发行前必须重新核对官方支持矩阵并实际验证。

## ARCH-001：产品角色与共享代码建议

**优先级：P2。状态：用户产品偏好已明确；最新建议方向未正式批准，完整方案未实现。**

**现状。** 当前工作区已经形成共享 C 库、Rust CLI、Rust FFI、Slint 原生 GUI，以及独立 HTML/JS + C/WASM 网页的基础。当前网页不是共享 Slint UI 的 Web 产物，也不是已经完成的 PWA。另一个仓库中的 Flutter 移动 GUI 是历史比较对象，不应默认把其代码或发布能力视为本工作区已经具备。

**最新建议方向（未正式批准、未实现）。** 原生桌面承担完整文件操作、批量任务和较大的转换工作；同源 Slint Web 提供免安装、移动和旧系统兼容入口；支持安装的环境再以 PWA 外壳提供独立窗口体验。以窗口空间选择布局，共享配置、状态和任务逻辑。无需为追求“支持移动”立即新增一套独立移动应用。

共享代码减少重复实现 UI 和业务逻辑的成本，不能消除各桌面 OS/CPU 的构建、打包、依赖部署和验收成本。Web 通常可以提供共同资源包，但仍要区分浏览器、显卡/驱动、文件权限和存储能力。

**验收。**

1. 原生与 Web 使用同一份核心配置模型和主要 Slint 组件。
2. 平台差异只通过明确定义的服务接口进入应用层。
3. 用户在两种入口选择同一输入和配置时，得到一致的转换结果或明确的能力差异说明。
4. 产品说明准确区分“桌面支持”“网页可运行”“可安装”“离线可用”四类能力。

**依赖。** ARCH-002、ARCH-007、ARCH-008、ARCH-015、ARCH-018。框架选择过程不再反复比较未满足维护偏好的路线；需要变更方向时，应记录新需求和测量依据。

## ARCH-002：共享应用层与平台服务

**优先级：P2。状态：建议，未实现完整分层。**

**现状。** 当前 Slint GUI 的应用逻辑同时包含窗口回调、rfd 文件对话框、std::fs、配置文件访问、后台线程和 C FFI 调用。当前 Web 则独立维护表单、VFS 路径、字体导入和同步转换。这使浏览器移植不能只给现有原生程序更换一个编译目标。

**建议架构。** 保留 C 的格式解析、转换、过滤、排版参数处理；保留共享 Rust 的配置、状态、任务协调和错误模型；将 OS 和浏览器能力移到平台服务层。下图是目标结构，图中的浏览器 Slint、预览渲染、PWA 和统一服务接口属于待实现部分。

~~~mermaid
flowchart TB
    UI["共享 Slint UI：参数、任务列表、时间轴、预览图像"]
    APP["共享 Rust 应用层：配置、状态、任务、校验、错误"]
    PLATFORM["平台服务接口"]
    NATIVE["Native 服务：文件、对话框、线程、持久化、更新"]
    WEB["Web 服务：File/Blob、JS 桥、Worker、存储、下载"]
    NC["原生 C 转换库"]
    WC["Emscripten C/WASM 转换模块"]
    NR["原生 libass 预览渲染"]
    WR["libass/WASM 预览渲染"]
    RGBA["统一预览结果：RGBA + 尺寸 + generation"]
    PWA["可选 PWA 外壳：缓存、安装、完整版本切换"]

    UI --> APP --> PLATFORM
    PLATFORM --> NATIVE
    PLATFORM --> WEB
    NATIVE --> NC
    NATIVE --> NR
    WEB --> WC
    WEB --> WR
    NR --> RGBA
    WR --> RGBA

    PWA --> WEB
~~~

**建议服务。** FileService 管理选取、读写、输出和文件身份；ConversionService 管理任务请求、结果和能力；FontService 管理字体文件及回退；PreviewService 输出图像；TaskService 管理执行和取消；SettingsStore 管理配置与 UI 状态；UpdateService 管理发行资源版本。服务命名和 trait 形式可以调整，但应使共享应用层不依赖 rfd、裸 FS 路径或 DOM。

**验收。** 原生和浏览器分别注入服务实现；共享应用层的源码不直接打开 OS 文件或启动原生线程；单元级 fake 服务可驱动“选择输入→配置→任务完成/失败→保存结果”的状态流。后续运行验证独立进行，本轮只记录结构。

**依赖。** ARCH-003、ARCH-004、ARCH-007。优先抽取确有两个实现的平台能力，避免先设计没有调用者的大型通用框架。

## ARCH-003：C ABI、FFI 所有权、版本与能力契约

**优先级：P1。状态：公开 C API 和 Rust 绑定已存在，独立组件兼容机制待补。**

**现状。** [公开 C 头文件](../../lib/include/danmakufactory.h) 已提供 create → configure → run → destroy 句柄生命周期，也保留 df_run_from_json 便利入口。输入路径由库复制；df_get_version 返回静态字符串；错误查询返回本线程 TLS 中的借用字符串，调用方不得释放，而且同线程后续 API 调用会使内容失效。Rust Context 用 Drop 管理句柄，错误转换成 Rust 拥有的字符串。

这些是可以用于多语言绑定的基础。产品版本字符串尚不能代替独立 DLL 或 WASM 的 ABI 兼容规则，也不能表达是否具备 PCRE2、字体度量、内存转换、取消或预览能力。

**建议契约。**

- 为 ABI 和配置分别提供明确的版本规则；新增函数、字段与行为变更怎样保持兼容，应有书面约定。
- 提供结构化 capability 查询，列出可用输入/输出格式、正则、字体度量及可选执行能力。具体 API 尚未实现。
- 若新增输出缓冲区，明确谁分配、谁释放、长度类型、有效期和失败时输出值；让释放函数在分配模块中执行。
- FFI 调用只传 UTF-8 字节、整数/浮点、明确长度和不透明句柄。检查嵌入 NUL、范围及生命周期，禁止依靠转换后的临时指针长期存活。
- Rust、Python、JS、Dart 等绑定使用同一错误码语义；不要各自重写“成功但忽略某配置”的容忍逻辑。

**验收。** 新旧绑定与核心的兼容组合有可执行的契约样例；不兼容组件在执行前被拒绝，错误包含组件版本和原因；能力不足可由 UI 在启动或配置时显示。每个借用/拥有指针在公开头文件中可找到唯一生命周期定义。

**依赖。** ARCH-005、ARCH-019、ARCH-020、ARCH-022。本轮没有新增 ABI/capability API，也没有证明独立更新已经安全可用。

## ARCH-004：规范配置、兼容输入和事务语义

**优先级：P1。状态：多项源码修复，待运行验证；极端字号边界另见 ARCH-024。**

**现状与本轮契约修复。** [配置解析](../../lib/src/config/parse.c) 已以 screen、danmaku、text、msgbox 嵌套对象作为规范形式；公开句柄 API 接受裸配置或含 config 的包装对象。配置加载采用合并语义，只覆盖出现的字段，加载后立即校验；失败时应保留已有上下文配置。

此前嵌套字段查找方式会忽略正确的嵌套配置；整体转小写会改变文件路径、字体名和正则表达式；标志位解析存在错误宽度写入。本轮源码分别改为正确的对象成员查找、仅键名大小写兼容及定宽范围校验。键查找辅助 df_json_get_member 优先精确键，然后兼容大小写；值不做整体大小写归一化。格式/模式等指定枚举值可以由各自解析器做兼容。

规范配置示例，省略字段使用已有值或初始默认值：

~~~json
{
  "config": {
    "screen": {
      "resolution": [1920, 1080],
      "display_area": 1.0,
      "scroll_area": 1.0
    },
    "danmaku": {
      "scroll_duration": 12.0,
      "fixed_duration": 5.0,
      "block_mode": ["TOP"],
      "block_list": ["CaseSensitiveRule"],
      "block_list_regex_enabled": false
    },
    "text": {
      "fontname": "Microsoft YaHei",
      "font_size": 38,
      "line_spacing": 0
    },
    "msgbox": {
      "show": true,
      "size": [500, 1080],
      "pos": [20, 0],
      "font_size": 38,
      "duration": 0.0
    }
  }
}
~~~

**兼容边界。** 老式平面字段和既有别名仍作为导入兼容路径；同时出现时，以嵌套字段优先，再考虑规范平面键和旧别名。新导出优先使用规范嵌套格式。resolution、size、pos 的推荐形式是两元素整数数组；旧字符串坐标仍应有界解析，保留有文档基础的分隔符兼容，并保留第二个坐标的正负号。不能因为是 GUI 控件生成的配置就省略核心校验。

**事务与所有权。** block_list 是含动态内存的字段。临时配置与旧配置可能短暂共享旧列表；失败只能释放本次新分配内容，成功替换后才释放旧列表。输入文件数组同样先完整解析到本地临时数组，再提交；不允许部分失败改变已有列表或发生 realloc(ptr, 0) 的悬空所有权。

**数值边界。** 配置、time_shift 和输入元数据要同时校验类型、有限值、整数性及目标范围。NaN 不能靠大小比较拒绝；有限但过大的持续时间也不能在秒转毫秒时转成越界整数。JSON 的较大 double 转 float 前也要检查范围。本轮已补多处有限性和时间范围检查，但不能据此宣称所有旧格式数值路径均已完成审计。

**验收。** 相同配置经 C 句柄、JSON 便利 API、Rust CLI、Slint 导出和浏览器导入后有一致效果；非法 section、数组元素、路径、非有限值和越界坐标返回错误；失败后上下文可继续使用旧配置；空模式数组能清空旧标志位；路径、字体名、区分大小写的规则原文保留。别名优先级与重复键策略应再写成完整 schema 契约。

**依赖。** ARCH-003、ARCH-020、ARCH-021、ARCH-024。当前存在多份入口适配，不能仅因 C 的键名兼容已经修复，就承诺所有 UI 导入器的兼容行为已经一致。

## ARCH-005：上下文、TLS 与全局字体注册表的线程约定

**优先级：P1。状态：公开头文件和字体头文件的范围表述仍不一致，待处理。**

**现状。** 公开 C 头文件声明 df_run_from_json 可独立并发调用，不同 Context 可独立使用；同一句柄不能被多个线程同时访问。错误信息是 TLS，工作线程必须在本线程及时读取并复制为拥有的字符串，再把结果交给 UI 线程。

与此同时，公开头文件第 5 点仍写“库内部不持有任何跨调用的全局可变状态”。[字体度量头文件](../../lib/src/text/measure.h) 明确说字体注册会修改全局注册表，只能在启动阶段、创建工作线程之前完成，运行阶段禁止注册。两份说明并未统一，因此不能把“不同转换上下文独立”扩大为“任何公开调用组合都没有全局状态或无需约束”。

**建议契约。** 保留转换上下文的隔离原则，明确注册表为启动前配置、运行时只读；定义何时认为任务已经进入运行阶段，以及动态导入字体如何处理。若产品允许运行期间换字体，应选择有锁的注册表快照、每个执行模块独立注册表或任务隔离等具体方案，不能只修改说明后继续无同步写入。

浏览器单 Worker 模块可以串行注册和转换；多个 Worker 各有独立 WASM 实例时应分别初始化字体。在共享同一原生进程且并发转换时，必须遵守上述只读阶段约定。

**验收。** 公开 API、measure.h 和绑定文档对 global/TLS/Context 的范围一致；调用线程复制错误后可安全发送跨线程消息；注册字体与任务执行有可观察的状态约束；不同 Context 的并发转换不会依赖可变全局配置。

**依赖。** ARCH-003、ARCH-012、ARCH-013、ARCH-020。本轮转入文档整理后暂停后续源码修复，没有修正这一公开线程说明，也没有新增同步实现。

## ARCH-006：转换服务及文件 API 到内存 API 的演进

**优先级：P2。状态：同步文件转换 API 已存在；内存接口是建议。**

**现状。** 当前核心运行信息描述输入文件路径、输出文件路径、配置和时轴偏移，执行时读取/写入文件。原生绑定直接传路径；浏览器绑定把用户文件写到 Emscripten VFS，再调用同样的 C 文件 API，最后读回输出。这足以共享核心，不需要为 Web 重写格式转换。

当前公开 API 没有返回 ASS 字节的内存转换入口、渲染帧接口、逐条进度回调或可取消调用。用文件/VFS 封装服务与直接拥有这些接口是两回事。

**建议演进。** 先以 ConversionService 包装既有路径 API，定义统一输入字节/格式提示/配置快照和结果内容/错误/能力等应用模型。待性能和生命周期需求明确，再评估 C 内存接口。新增接口应复用现有解析与写出过程，不复制一条独立转换管线。

预览可先通过临时 ASS 或 VFS 输出复用核心；需要频繁重生成时再衡量字节缓冲区接口的收益。配置 JSON 是稳定边界的候选，但大文件数据不应塞进庞大 JSON 字符串。

**验收。** 原生路径实现和浏览器 VFS 实现隐藏在服务之后；资源清理覆盖成功、失败和取消；同一请求模型支持导出结果和预览输入；内存接口若加入，应有长度/分配上限/释放函数/OOM 行为的契约。

**依赖。** ARCH-003、ARCH-009、ARCH-010、ARCH-013。是否新增内存 API 由真实瓶颈决定，不是 Web 支持的前置硬要求。

## ARCH-007：共享 Slint UI 与 Rust 应用逻辑

**优先级：P2。状态：当前 Slint 源码面向原生桌面，Web 适配尚未实现。**

**现状。** [Slint GUI](../../gui/slint/) 已有 .slint 窗口、参数、文件列表、日志和批量进度。Cargo/build.rs 连接本地 Rust 绑定和原生 C 库；main.rs 使用 rfd、std::fs 和 std::thread。配置构建过程还直接读黑名单文件。这些具体依赖需要移动，不能认为编译同一 main.rs 就自动获得 Web 程序。

**建议。**

- 共享 .slint 组件、视图模型、配置快照和主要状态机。
- native 入口使用原生 FileService、TaskService 和 FFI；Web 入口使用浏览器实现和 JS 桥。
- 用明确的 feature/target 模块选择平台实现，避免在业务函数中到处分散 cfg 判断。
- UI 只发送意图，例如“选择输入”“转换当前任务”“导入字体”，不保存可执行的裸 OS 操作。
- 保留 .slint 是声明式 UI 语言这一事实。愿意 Rust 并不等于 UI 文件全部由 Rust 编写。

**验收。** 原生和 Web 入口确实引用相同的 UI 和共享状态模块；Web 依赖图不会拉入原生 C 链接、rfd 同步窗口或仅原生文件系统；核心错误与日志展示一致；窄屏变化在共享组件中实现。

**依赖。** ARCH-002、ARCH-008、ARCH-013、ARCH-017。用户希望共享界面，故独立 HTML 完整 UI 不再是默认新增主线；现有 HTML 可继续作为诊断和回退基础。

## ARCH-008：Rust/Slint UI WASM 与 Emscripten C/WASM 的薄 JS 桥

**优先级：P2。状态：C/WASM 构建目标与 JS 绑定已存在；双模块 UI 集成未实现。**

**现状。** [xmake.lua](../../xmake.lua) 定义 Emscripten 核心构建，[JS 绑定](../../bindings/javascript/danmakufactory.mjs) 封装 C 调用、VFS 转换和字体注册。浏览器无法直接加载原生 DLL/SO；C 源码需要另编译成可运行的 WASM。

**建议路线。** Rust + Slint 编译为 UI WASM；C 保持现有 Emscripten WASM；薄 JS 桥处理模块初始化、文件字节、Worker 请求/结果和下载。JS 不重新实现转换算法，也不需要另外维护完整参数业务界面。

两个 WASM 通常拥有各自的线性内存和运行环境。一个模块中的地址不可以直接当作另一个模块的指针使用。应采用 JS ArrayBuffer/Uint8Array、显式复制或经过设计的共享缓冲机制，并记录所有权。不要默认把 Rust wasm32-unknown-unknown 与 Emscripten 的 ABI、FS、线程和链接方式当成相同运行环境。

**建议桥接请求。** requestId、generation、operation、configSnapshot、inputId、inputBytes、formatHint、fontSetVersion；响应包含 result/error、generation、必要的输出字节和诊断。字段名称未确定，也不是现有公开接口。大数据使用可转移的缓冲区时，明确发送后所有权变化，避免再次读取已转移内存。

**验收。** 模块初始化错误可显示；UI、转换和预览组件的版本可查询；重复初始化或任务失败不泄漏 VFS、内存和 Object URL；没有跨模块裸指针；任务响应按 requestId/generation 关联；用户内容可在浏览器本地完成转换。

**依赖。** ARCH-003、ARCH-007、ARCH-009、ARCH-013、ARCH-018。shared memory/多线程 WASM 需要额外浏览器和托管条件，第一版不应把它作为旧系统兼容的必需基础。

## ARCH-009：文件身份、路径、VFS 与输出保护

**优先级：P1。状态：已有实现并有源码修复，统一文件服务待实现。**

**现状。** 原生 GUI 使用 OS 路径、输出目录和文件名；本轮对原生输出与输入相撞、批量同名文件的目标名称预留等问题作了源码处理，仍需运行验收。Web 通过用户选择的字节写入 /tmp，字体写入 /fonts，再读回输出并下载。OS 绝对路径、浏览器 File 和 VFS 路径属于不同层。

**建议边界。**

- 应用层使用逻辑 inputId/jobId 和可显示名称；原生路径或浏览器文件对象由 FileService 持有。
- 每次 Web 转换使用独立 VFS 目录/文件名，避免相同文件名、并发任务和上次失败残留互相覆盖。
- 导出由输出内容加建议文件名描述；浏览器最小路径是普通下载，目录访问是可选增强。
- 原生先规划整批输出，再检测与任一输入、已有文件和其他输出冲突。要统一 overwrite/rename/error 策略。
- 清理临时输入、输出、字体缓存和下载 Object URL；保留字体的生命周期应单独定义，不能顺手删除仍在使用的文件。
- 用户选择的本地文件只在本地处理的默认模式下使用；若未来增加云端服务，应把上传作为明确的新操作。

**验收。** 中文、空格、大小写不同路径、重名输入、同格式输入输出、取消/失败再重试均不会覆盖原文件或读到旧结果；浏览器不要求直接访问完整目录才能完成基本转换；导出失败可区分转换失败和保存失败。

**依赖。** ARCH-004、ARCH-006、ARCH-013。路径身份在 Windows/Linux/macOS 的规则不同，不应只通过把字符串转小写实现跨平台等价判断。

## ARCH-010：真实字幕预览与 libass 候选管线

**优先级：P2。状态：C 文本度量已存在；完整字幕预览尚未实现。公开预览能力前必须满足本契约。**

**现状。** FreeType、HarfBuzz、Fontconfig 的 text/measure 模块用于计算文字宽度，影响转换排布。它没有绘制 ASS 帧，没有视频时间轴，也没有生成供 Slint 显示的字幕图像。当前 GUI 和网页不能因为有字体导入或“精确测量”标记就声称具有真实字幕预览。

**候选管线。**

~~~mermaid
flowchart LR
    I["输入弹幕 + 不变配置快照 + 字体集"] --> C["同一 C 核心转换"]
    C --> ASS["正式输出同源 ASS 字节"]
    ASS --> R["libass：指定 viewport 与 timestamp"]
    F["同源字体文件与回退策略"] --> R
    R --> IMG["字幕 RGBA 帧 + 尺寸"]
    IMG --> SLINT["Slint Image/Texture 预览区"]
~~~

真实 ASS 预览需要使用能解释 ASS 语义的渲染器；libass 是本轮主要候选，不是唯一允许的实现。建议桌面使用原生 libass，Web 使用 libass/WASM。JASSUB 是历史讨论中的候选封装，具备按时间戳渲染的思路，可用于无视频的字幕预览；具体版本、接口和浏览器覆盖仍待选择验证。没有要求 Slint 自己复刻 ASS 排版、描边、阴影、移动、位置与特效。

预览服务首先输入正式输出的 ASS，按 timestamp 返回字幕图层，可叠加纯色、棋盘背景或用户选定静态背景。若将来加入视频，只把媒体解码/播放作为另一服务，字幕渲染接口继续独立。

**验收。** 对固定 ASS、字体文件、viewport 和时间戳，原生/Web 预览的主要位置、移动轨迹、字号、透明度、描边和特效符合 libass 结果；预览中的配置与导出配置一致；时间单位明确，避免秒/毫秒混用；用同一输入生成的导出文件能解释预览结果。跨平台像素完全相等是否合理应由固定字体和渲染版本实测决定，不能预先承诺。

**依赖。** ARCH-006、ARCH-011、ARCH-012、ARCH-013、ARCH-020。框架能显示图像只解决最后一环，不自动提供真实 ASS 预览。

## ARCH-011：时间轴、实时参数更新、去抖与过期结果

**优先级：P2。状态：建议，未实现。**

**现状。** 当前源码未见真实预览状态机。把每次参数输入立即同步调用 C 转换，再立即刷新图像，会阻塞输入，也可能使较早任务覆盖较新设置。

**建议状态。** 每份输入、配置快照和字体集组成一个 preview generation。参数或输入变化时增加 generation；后台生成 ASS；仅当返回 generation 仍匹配当前请求时接受结果。时间轴移动只重新渲染当前 ASS 的帧，不必重新解析和转换全部输入。需要取消的长任务与丢弃旧结果分别实现。

参数编辑可采用约 150–300ms 的初始去抖窗口，这是待测的体验参数；滑块和文字输入可以有不同策略。点击明确的“预览/导出”动作可立即提交。不要把去抖值当作已经确定的性能保证。

缓存 ASS 时，键至少包含输入内容标识、配置快照、核心能力/版本与字体集版本；缓存帧时再包含时间戳、viewport 和 renderer 设置。限制缓存大小，避免保存每个播放时间点的大幅 RGBA 图像。

**建议错误流。** 新配置非法时保留上次有效预览，并明确提示其对应的旧设置；新任务失败显示诊断而不是白屏；预览与导出用同一校验模型。生成任务和渲染任务分别计时，定位瓶颈。

**验收。** 连续快速改参数时 UI 可继续响应；旧结果不会覆盖新配置；拖动时间轴不会触发无意义的全量转换；任务关闭后释放资源；预览显示其来源配置/输入版本；无效参数不会悄悄导出旧配置。

**依赖。** ARCH-010、ARCH-012、ARCH-013、ARCH-020。generation 丢弃只防止旧结果显示，本身不会中断已经运行的 C 计算。

## ARCH-012：字体服务、度量与渲染的一致性

**优先级：P1。状态：度量模块有多项源码修复；字体契约和真实渲染一致性待完成。**

**现状。** [text/measure.c](../../lib/src/text/measure.c) 使用 FreeType/HarfBuzz，原生有 Fontconfig 路径，无 Fontconfig/WASM 使用显式字体注册。当前源码已补字体创建失败、缓存失败、像素尺寸设置、HarfBuzz 缓冲分配、advance 累积范围、FT Face 引用释放及 Fontconfig TTC face index 等处理。缺失字形返回 -1，调用者可能进入估算回退。

“度量上下文可用”“注册字体成功”“某条文字使用精确度量”和“libass 按相同字体完成真实渲染”不是同一状态。HarfBuzz 单字体 advance 不覆盖 libass 的完整多字体回退、ASS 行为、换行、样式与比例设置。因此网页的“精确测量”状态需要进一步限定含义。

**建议字体服务。**

- 保存字体文件内容标识/hash、family、TTC face index、源路径/逻辑 ID、字体集版本和加载结果。
- 转换度量与 libass 预览尽量使用同一份字体字节和可解释的匹配规则。
- native 可以系统字体发现作为便利；Web 使用打包字体或手动导入作为基础。系统字体枚举、直接本地字体读取属于可选权限能力。
- 明确 C 度量在 native Fontconfig 路径和显式注册路径的差异；现有 register_font 在有 Fontconfig 的原生环境无实际效果，不能宣称各平台注册行为已经相同。
- 动态换字体遵守 ARCH-005 的注册阶段约定；更换后旧缓存和预览 generation 失效。
- 字体加载失败、缺字、无法精确度量和采用渲染回退应有分别可理解的提示。

**验收。** 中文、英文、组合字符、emoji/缺字、TTC 多 face 的样例可解释实际选用字体；转换碰撞判定与预览误差有明确观察标准；不具备系统字体权限的浏览器仍能通过导入文件工作；非法/过长字体名和路径被拒绝，OOM 不进入无效字体 shape 调用。

**依赖。** ARCH-005、ARCH-010、ARCH-011、ARCH-020。尚未实现字体快照、多字体回退匹配或跨渲染模块统一缓存。

## ARCH-013：后台执行、Worker、进度与取消

**优先级：P2。状态：原生后台线程已存在；浏览器转换仍在主线程，完整取消未实现。**

**现状。** Slint main.rs 在 std::thread::spawn 中逐文件转换，用 invoke_from_event_loop 回传 UI 状态，进度以处理文件数更新。局部 stop_flag 在文件之间检查，但当前不应视为完整用户取消接口，更不能中断运行中的同步 C 调用。浏览器 app.js 直接同步 ccall df_run_from_json，会占用主线程。

**建议。** Native TaskService 持有任务执行器和 Context；Web TaskService 在 Worker 中初始化 C/WASM 和需要的字体/VFS。UI 只接收状态消息。第一阶段可串行转换，避免多个大文件同时复制产生峰值内存；并发度由实测控制。

进度先准确表示“已完成文件/总文件”；没有底层记录级进度时，不制造平滑百分比。若新增 C 进度回调，应约定频率、线程、回调内可执行操作和错误处理。

取消分三级描述：停止后续文件；丢弃当前任务返回结果；协作中断当前核心转换。前两项不能冒充第三项。终止 Worker 可回收模块，但涉及重新加载、字体初始化及未完成结果，需要独立策略；native 不应强杀线程后继续使用被中断的 Context。

**验收。** 转换大输入时窗口/网页继续响应；错误在执行线程中复制并回传；取消后不会再导出过期结果或改变新任务进度；每任务资源最终回收；线程/Worker 生命周期与窗口关闭一致。

**依赖。** ARCH-005、ARCH-008、ARCH-009、ARCH-011。浏览器多线程 WASM 与 Web Worker 是不同能力，使用一个 Worker 执行同步核心并不要求核心内部开线程。

## ARCH-014：配置持久化、UI 状态与迁移

**优先级：P2。状态：原生配置保存/导入已存在；统一持久化层未实现。**

**现状。** Slint GuiConfig 有自身 Rust 字段模型，导出时生成嵌套 config。导入黑名单规则和路径有 GUI 辅助字段；配置构建会读黑名单文件。当前 Web 以表单组织输入，未形成同源 Slint 的统一 SettingsStore。不能直接把 OS 配置文件路径搬到浏览器。

**建议分离。**

- 核心配置：转换结果相关参数，按规范嵌套 schema 导出，可跨入口交换。
- UI 状态：窗口尺寸、面板展开、最近输入显示、预览时间、当前主题等；独立版本与迁移。
- 平台资源引用：本地文件路径、浏览器文件授权、导入字体内容等；由平台存储管理，并处理资源不可再用。
- 用户预设：显式命名、导入导出，包含必要版本/能力说明；不能依赖某台机器的绝对路径才能理解。

Native 可用配置文件；Web 可用 IndexedDB 存二进制/较大状态，少量简单设置可用 localStorage。具体存储方案和配额处理未实现。浏览器存储可能被清理、禁用或达到限制，保存失败不应破坏当前转换；提供手动导出预设作为恢复手段。

**验收。** 合法配置跨 CLI、原生 GUI、Web 往返不丢失核心字段；未知未来字段的保留/拒绝策略明确；旧配置迁移不会静默改含义；UI 状态与核心配置分离；无法恢复资源时提示重新选择；浏览器隐私模式或存储失败仍可完成一次转换。

**依赖。** ARCH-004、ARCH-007、ARCH-009、ARCH-019、ARCH-021。GuiConfig 与核心初始默认值的差异需确认是产品预设还是兼容缺陷，并记录来源；不能未经确认就视为已批准的产品预设，也不能称为完全一致而实际不同。

## ARCH-015：平台支持与发行验收矩阵

## ARCH-018：SPA、PWA 安装、离线和自动更新

**优先级：P2。状态：现有 HTML 单页基础已存在；PWA 外壳和更新策略未实现。**

**验收。** 在线首次使用、第二次离线使用、下载中断、缓存不完整、旧版本任务期间发现新版、更新后设置恢复均有明确行为；旧浏览器无法安装时可正常网页使用；更新失败仍可本地转换。

## ARCH-024：本轮暂停后续源码修复时仍存在的字号与估算宽度边界

**优先级：P1。状态：已确认，未修复。**

**现状。** config/validate.c 对 text.font_size 和 msgbox.font_size 目前只要求大于 0，公开 setter 可以传入 INT_MAX；base/string.c 的 getStrHei 仍用 int 做字号加法，getStrLen 用 int 计数并计算 cnt × 有效字号后再除以 1.2。很大字号或很长 JSON 文本会使中间整数运算溢出。字体精确度量失败时仍可能进入这条估算路径。

ASS 部分的组合时间边界、宽整数计算或负宽度拒绝，即使有其他源码改动，也不能证明上述先发生的 C int 运算已经安全。该风险在本轮转入文档统合而暂停后续源码修改时仍保留，不能写入“已经修复”列表。

**建议下一步。** 为配置字号设与输出语义相容的实用上界；SHRT_MAX 是讨论过的候选，不是已落盘契约。估算计数使用能承受输入长度的类型，乘法/加法采用宽类型或 checked arithmetic，先范围检查再转 int；过大/无效结果明确返回失败，禁止依靠 signed overflow 后的负数判定。

**验收。** 公共 setter 与 JSON 输入都拒绝超上界字号；很长文本在精确度量可用/不可用两条路径都不会整数溢出；估算返回失败能被排布/输出层识别；新增测试在解除禁止运行限制后执行。准确修改文件、严重性和原始证据以代码台账为准。

**依赖。** ARCH-004、ARCH-010、ARCH-012、ARCH-020。这个 checkpoint 是后续源码工作先处理项；本轮只记录，没有补源码或执行验证。

## ARCH-025：分阶段迭代与依赖检查
