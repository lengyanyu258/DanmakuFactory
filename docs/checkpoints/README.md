# DanmakuFactory 设计与审查 checkpoints

本目录保存 2026-10-01「比较 Slint 与 Flutter」及 2026-10-03 当前代码 Review 的核心内容：用户约束、选型变化、架构方案、已发现问题、源码修复、残余风险、发布路线和验收计划。目标是让下一次继续工作时可以按 checkpoint 恢复，而不必重新依赖聊天记忆。

本轮以现有文档与公开 API 为兼容性基准；没有执行编译、构建、测试或 GUI/浏览器运行验证。各文档中的“源码已改”不表示已通过验证。最新讨论建议是 **Rust + Slint 为主桌面入口，共享 Slint UI 产出 Web/PWA 兼容入口，并抽离平台服务**；这是基于用户偏好的建议，不表示整套方案已实现或用户已批准全部阶段。

## 文档状态规则

| 状态 | 含义 |
|---|---|
| 用户已确认 | 用户直接给出的偏好或约束，例如按现有文档/API 兼容审查 |
| 历史讨论/建议 | 基于当时条件的技术判断；不能当作当前已落实功能 |
| 待处理/待实现 | 仍有明确代码或交付缺口 |
| 部分完成 | 已有基础或一侧接线，尚未闭合所有条件 |
| 已改源码，未运行验证 | 修改可在工作区看到，未有本轮运行证据 |
| 历史验证/测量 | 只适用于记录中的时间、版本、环境与产物 |
| 验证通过 | 须填写实际执行环境、版本和结果；本轮没有功能验证通过项 |

严重等级 P0/P1/P2/P3 以[审查台账定义](03-code-review-and-fixes.md#严重等级状态与责任)为准。发布/架构文档的优先级表示交付顺序或发布门槛，不能把一个未承诺的新功能直接算成现有产品缺陷。

## checkpoint 维护方式

保持 DEC/ARCH/REV/REL/CP ID 稳定。在原条目下追加日期、实现/提交、环境、验证结果和残余风险；新增事项使用新 ID。源码修复与运行验证分别关闭，历史问题和建议前提保留。

这些 ID 是文档内部记录，没有自动创建外部 issues，也没有代替用户决策。遇到需求歧义可以问用户；现有文档与 API 已明确的兼容义务应直接落实。
